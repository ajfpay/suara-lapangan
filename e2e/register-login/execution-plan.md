## 1. Topology & Isolation Strategy

### Single-Worker Topology Recommendation

For this engagement, the planned implementation executes via a **Single Worker** paired with a **Single Verifier**, with **zero git worktrees** and **zero GitHub PR stacking**.

### Architectural Justification

1. **Self-Contained Scratch Directory**:
   All test code, runner configuration, credential helpers, and evidence generators are located strictly within `~/repos/.scratch/register-login-e2e/`.
2. **Untouched Target Repositories**:
   Neither `/home/ubuntu/repos/suara-lapangan-hackathon-pr` nor `/home/ubuntu/repos/e2e` receives code modifications, branch checkouts, or commit additions.
3. **Absence of Git Overhead**:
   Worktrees provide isolation when multiple git branches in the same repository are modified concurrently. Because the scratch directory is not a git repository and application repositories are strictly read-only, allocating git worktrees would introduce unnecessary complexity, disk allocation, and branch synchronization overhead with zero isolation benefit.
4. **Deterministic Sequential Execution**:
   Because Scenario C depends directly on the fresh account generated by Scenario A (Ticket 03), a single worker executing sequentially (01 -> 02 -> 03 -> 04 -> 05) ensures test database coherence and eliminates multi-agent state race conditions.

## 6. Implementation Batch Order and Stop Protocols

Once Gates 1–3 are approved, execution will proceed through the 5 tickets in strict order:

```
[Ticket 01: Framework Skeleton] 
       ↓
[Ticket 02: Credential Bootstrap] 
       ↓
[Ticket 03: Scenario A & B Tests]
       ↓ (Stop Rule: Fresh registration failure halts suite)
[Ticket 04: Scenario C Inbox & Login Tests]
       ↓ (Stop Rule: Anti-bot challenge or 5m email timeout halts suite)
[Ticket 05: Consolidated Evidence Report]
```

### Stop Rule Protocols:
1. **Anti-Bot Encountered:** Worker halts immediately, takes screenshot `antibot-challenge.png`, outputs error notice, and aborts.
2. **Fresh Registration Error:** Worker halts immediately, captures diagnostic log, and aborts. Reusing the old account is strictly forbidden.
3. **Inbox Timeout (300s):** Worker marks run `BLOCKED`, records delivery delay, and exits without database modifications.
4. **Credential Absence:** Worker halts immediately if Akeyless item is missing.
